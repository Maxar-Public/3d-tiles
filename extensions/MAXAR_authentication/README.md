## Overview

The `MAXAR_authentication` extension enables verification of the integrity and authenticity of files within a tileset through digital signatures.

The extension references external signature files containing cryptographic signatures for validating tileset content. This enables verification that tileset files have not been tampered with and originate from a trusted source.

The extension supports ECDSA (Elliptic Curve Digital Signature Algorithm) with NIST curves and Ed25519 signature algorithms, which provide strong security properties, efficient performance, and native support on Windows platforms through the CNG (Cryptography API: Next Generation) interface. Their support for pre-hashing and streaming workflows makes them particularly suitable for signing large files.

To support platforms with constrained resources, the extension also supports partial signatures. These verify a selected byte range within a file and are useful for large files, real-time validation, or devices with limited CPU or battery capacity.

**Note**: Data URIs are not allowed for the signature manifest reference. Since the signature manifest typically needs to sign the tileset.json file itself, the signature manifest must be created after the tileset.json is finalized, preventing the use of embedded data URIs which would create a circular dependency.

## Extension Properties

The extension includes the following properties in the tileset:

- `algorithm`: The signature algorithm used for authentication. Supported algorithms are:
  - `ecdsa-p256-sha256`: ECDSA with NIST P-256 curve and SHA-256 hash (~128-bit security)
  - `ecdsa-p384-sha384`: ECDSA with NIST P-384 curve and SHA-384 hash (~192-bit security)
  - `ecdsa-p521-sha512`: ECDSA with NIST P-521 curve and SHA-512 hash (~256-bit security)
  - `ed25519ph`: Ed25519 with pre-hashing for efficient verification of large files (Note: not supported on all platforms)
- `keyId`: A unique identifier for the public key used to verify signatures. The value must uniquely identify the key within the system. The key ID should be generated to guarantee uniqueness (for example, using a UUID, a random string, a systematically generated id with namespace context, or a cryptographic hash of the key material). It must never contain the key itself or any reversible encoding of the key.
- `signatureManifest`: The URI (or IRI) to the signature manifest containing cryptographic signatures for selected files linked from this tileset. All signatures use the algorithm specified in the `algorithm` property.
- `signature`: The URI (or IRI) to the file containing the cryptographic signature of the signature manifest. The file contains raw binary signature bytes generated using the algorithm specified in the `algorithm` property, and can be validated with standard tools such as OpenSSL. This signature prevents tampering with the manifest, such as removing signed file entries. The signature file should not be included in the signatureManifest since it is generated after the signatureManifest is finalized.

All properties are required.

### Signature Manifest: File Inclusion Rules

The following rules govern which files are included in the signature manifest and which files must be excluded.

#### Files that MUST be included

- **The tileset file itself**: The tileset JSON file that contains the `MAXAR_authentication` extension.

#### Files that MAY be included

- **Tile content files** (highly recommended): Files referenced by the `uri` property in `content` objects (as defined in `content.schema.json`) within the tiles of the 3D Tiles hierarchy. This includes:
  - Files referenced by `tile.content.uri` (for explicit tiles)
  - Files referenced by `tile.contents[].uri` (when using multiple contents)
  - For implicit tiling: When a root tile uses implicit tiling, both tile content files and subtree files are referenced via template URIs that contain variables `{level}`, `{x}`, `{y}`, and optionally `{z}` for octrees. The `content.uri` property specifies the template for tile content files, and the `subtrees.uri` property (defined in the `subtrees` property in `tile.implicitTiling.schema.json`) specifies the template for subtree files. Each actual file is generated by substituting the appropriate coordinates into these templates.

- **Transitive dependencies**: Files that are dependencies of the directly linked files, such as external textures or other resources referenced by tile content.

- **External metadata schemas**: Schema files referenced by the tileset's metadata (e.g., via `schemaUri` properties).

- **Extension-referenced files**: Files referenced by extensions, including both tileset-level extensions (e.g., external resources required by 3D Tiles extensions) and extensions within tile content (e.g., external files referenced by glTF extensions).

#### Files that MUST NOT be included

- **Data URIs**: Content referenced via data URIs (e.g., `data:application/octet-stream;base64,...`). Data URIs are authenticated implicitly through the signature of the tileset file that contains them and therefore do not require a separate signature entry.

- **External tilesets**: Files from external tilesets referenced via `tile.content.uri` pointing to another tileset JSON file. External tilesets SHOULD have their own `MAXAR_authentication` extension if authentication is required.

- **The signature manifest file**: The signature manifest file referenced by the `signatureManifest` property, since including it would create a circular dependency where the file's content depends on its own signature.

- **The signature file**: The file referenced by the `signature` property, since it is generated after the signature manifest is finalized.

## Signature Manifest Format

The signature manifest file referenced by the `signatureManifest` property contains an array of signature objects for specific files within the tileset.

The signature manifest file must include:

- `signatures`: An array of signature objects, each providing authentication information for specific files

Each signature object must include:

- `uri`: The URI of the file being authenticated
- `signature`: The cryptographic signature for the entire file (Base64-encoded)

Optionally, a signature object may include:

- `partialSignature`: An object containing signature information for a specific byte range within the file, which includes:
  - `byteLength`: The number of bytes covered by the signature (required)
  - `byteOffset`: The byte offset from the beginning of the file where the signed range starts (optional, defaults to 0)
  - `signature`: The cryptographic signature for the specified range (required, Base64-encoded)

#### Guidance: Full vs partial signatures

Full-file signature is authoritative. It is the only way to fully guarantee that a file is unchanged and originates from the correct source. Clients should verify the full-file signature whenever feasible.

A partial signature offers a less computationally expensive way to perform basic verification. It verifies a selected byte range and is useful for large files, real-time validation, or devices with limited CPU or battery. Keep the signed range small—no more than a few kilobytes—and choose a representative portion of the file, such as the JSON section of a glb.

Including partial signatures broadens dataset compatibility to resource-constrained devices and real-time applications. Producers should include them when targeting environments with limited CPU resources or battery capacity, or when enabling quick early checks for large files. Omitting partial signatures limits dataset usage to high-resource environments where full-file verification is always feasible.

Partial signatures enable fast-fail scenarios with full authority: if the partial signature fails, the file is definitively tampered and no further verification is needed. However, a passing partial signature cannot guarantee the file is untampered—only a full-file signature verification provides that guarantee. On resource-constrained devices or in real-time scenarios where full-file verification may not be feasible, a passing partial signature offers a reasonable confidence check, though producers and consumers must understand it does not provide complete assurance.

## Base64 encoding

All binary signatures represented as strings in the signature manifest use standard Base64 encoding (RFC 4648 §4) with the '+' and '/' alphabet. Padding is applied to Base64 encoded strings only when the final block contains fewer than three input bytes: with two bytes append "=", with one byte append "=="; with three bytes no padding is added. All Base64 encoded fields expect padding when needed.

## Optional vs Required

This extension is optional; it should be listed in the tileset JSON top-level `extensionsUsed` array and not in `extensionsRequired`. This allows tilesets to provide authentication information for clients that support verification while remaining compatible with clients that do not implement signature verification.

## Examples

### Tileset JSON example

```json
{
  "asset": {
    "version": "1.1"
  },
  "extensions": {
    "MAXAR_authentication": {
      "algorithm": "ecdsa-p384-sha384",
      "keyId": "a871c47a7f48a12b38a994e48a9659fab5d6376f3dbce37559bcb617efe8662d",
      "signatureManifest": "tileset.sig.json",
      "signature": "tileset.sig"
    }
  },
  "extensionsUsed": [
    "MAXAR_authentication"
  ],
  "geometricError": 1000,
  "root": {
    "boundingVolume": {
      "region": [-1.3197004795898053, 0.6988582109, -1.3196595204101946, 0.6988897891, 0, 20]
    },
    "geometricError": 500,
    "refine": "REPLACE",
    "children": [...]
  }
}
```
